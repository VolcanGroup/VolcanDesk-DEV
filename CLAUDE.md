## Architecture

**Client/server split**: `frontend/src/services/api.js` is the single fetch wrapper; `API_BASE_URL` is derived from `window.location.hostname` (works from any machine on the LAN, not hardcoded to localhost). Every resource has a matching service module in `frontend/src/services/`.

**Auth model (hardened 2026-08-26, was previously headers-only with plaintext passwords)**: still no real session/cookie — the client sends `x-user-id`/`x-user-role` headers read from `localStorage['tms_current_user']`, and the server trusts them at face value (`req.user` middleware in `server.js`). What changed: passwords are now bcrypt-hashed (`User` model's `beforeSave` hook in `db.js`; legacy plaintext rows are migrated transparently on their next successful login via `isBcryptHash()`), there's a real `POST /api/auth/login` route so the password never has to leave the server or be fetched by the client, and a `requireAuthenticated` middleware (valid `x-user-id` + a real role string) now gates `GET /api/tickets`, `GET /api/users`, and all ticket/notification write routes that previously had **no gate at all** (any anonymous `curl` could read every ticket, every password, or write to any ticket). `GET /api/users` also now excludes `password` from every response. **The underlying spoofability is unchanged** — anyone who can set arbitrary headers can still claim to be any user/role; closing that needs real sessions/JWT, out of scope of this pass. `RESTRICTED_TICKET_FIELDS` (ticket fields only internal roles may set) is enforced on `PUT` but **not** on `POST /api/tickets` — known gap, not yet fixed.

**New role `group_admin` (added 2026-08-27) — admin scoped to a single Volcán Desk group**: `User.role` gained `group_admin` alongside `admin`/`agent`/`client` (`supervisor` existed briefly, removed entirely 2026-09-14 — see below), paired with a new `User.admin_group_id` column that pins the account to exactly one group. A `group_admin` behaves like a full admin — sees/manages that group's tickets, and can edit that group's Tipos/Categorías/Prioridades/Productos/`CampoCatalogo`/`ReglaFlujo` — but never touches catalogs belonging to another group or to Voltik, and can never grant itself/anyone the global `admin` role. Backend: `requireAdminOrGroupAdmin` middleware and `getGroupAdminScope()` helper (`server.js`) gate and scope `POST /api/config` (group-diffing logic) and all `campos-catalogo`/`reglas-flujo` CRUD routes (via a `resolveTipoGroup()` helper); `checkTicketAccess`/`getUserGroupContext`/`isAuthorizedResolverGroupMember` all fold `groupAdminScope` in as an implicit group membership. `POST/PUT/DELETE /api/users` briefly used `requireAdminOrGroupAdmin`, got a real privilege-escalation hole (a `group_admin` could `PUT` their own account to `role: 'admin'`, no scoping at all) — **fixed 2026-08-27** by switching those three routes to `requireAdmin` outright. **Reopened for `group_admin` 2026-09-14, at the user's explicit request, but properly scoped this time**: all three routes are back on `requireAdminOrGroupAdmin`, and a new `isUserInGroupAdminScope(scope, targetUser)` helper (used by both `PUT`/`DELETE`) rejects anything outside the caller's own group — `targetUser.role === 'admin'` is always rejected (no path to the global role), `group_admin` targets must have `admin_group_id === scope`, `agent` targets must have `scope` in their `groups`. `POST` now also accepts `data.role === 'group_admin'` (previously only `'agent'`), still force-writing `admin_group_id`/`groups` server-side from the caller's own scope — a `group_admin` can create/edit/delete peer `group_admin`s of their own group now, never `admin`, never another group. The `GET /api/config`/`GET /api/campos-catalogo`/`GET /api/reglas-flujo` routes were also unauthenticated and unfiltered (any caller, including a `group_admin`, got every group's — and Voltik's — catalog data, UI-filtered only) — **fixed 2026-08-27, then corrected same day** after breaking the "Todos" ticket view. First pass filtered these three routes to just the caller's own `admin_group_id` (`getGroupAdminScope()`) when `req.user.role === 'group_admin'` — but a `group_admin` can see tickets from OTHER groups too (any ticket they created as requester, regardless of its resolver group; `checkTicketAccess`/the ticket-list query already allow this), and the narrow filter meant Prioridad/Categoría/Tipo for those other-group tickets no longer resolved to a label — the raw internal `value` (e.g. `"baja__<grupoId>"`, `"c1787787056420"`) showed instead, reported live in the "Todos" table. Fixed by `getConfigVisibleGroupIds(user)` (`server.js`, right after `getUserGroupContext`): unions `getUserGroupContext().allowedGroups` (group membership + `AreaAccesoExtra`) with every `resolver_group_id`/`group`/`area_origen_id`/`apoyos[].grupo_solicitado` found across that user's own `createdBy` interno tickets — i.e., every group whose label they might actually need to render, not just the one they administer. **Write routes are unaffected and deliberately stay narrow** — `POST /api/config`/`campos-catalogo`/`reglas-flujo` still use `getGroupAdminScope()` (single `admin_group_id`), since editing another group's catalog should still be blocked even if you can see one of their tickets. Not handled by `getConfigVisibleGroupIds`: a ticket visible only via an *active apoyo* to one of the user's groups (rather than group membership or being the creator) — a narrower, currently-unreported gap, worth revisiting if it surfaces. Stays open/unfiltered for every other caller (including the pre-login `GET /api/config` call `App.jsx` makes), so Voltik's behavior is untouched throughout. Frontend: a shared `frontend/src/components/GroupScopeGate.jsx` (`GroupScopePicker`/`GroupScopeReassign`/`GroupScopeBreadcrumb`) drives "pick your group" UX for `group_admin` and reassignment UX for `admin` across `FormFieldsConfigPage.jsx`, `FlowsConfigPage.jsx`, and the Types/Categories/Priorities config pages in `Settings.jsx`; `ticketService.js`'s `getUserGroupsForScoping(currentUser)` and the `currentUser.role === 'group_admin' ? [currentUser.admin_group_id] : currentUser.groups` pattern (repeated in `Tickets.jsx`/`TicketTable.jsx`) extend "my group" scoping to dashboards, the `deskRoleViewMatch` view tabs, and CSV export gating. Any future change to admin-gated routes, Volcán Desk catalog pages, or the "Recurring bug pattern"/"Group semantics" sections below needs to account for this as a third group-scoping dimension, alongside `resolver_group_id`/`area_origen_id`/apoyos.

**Backend recomputes ticket `activities` server-side, discarding whatever the client sent** — `PUT /api/tickets/:id` does `delete data.activities` up front and rebuilds the array itself from `TRACKED_TICKET_FIELDS` plus a few special-cased blocks (escalation, apoyo-requested). **If you add client-side logic in `ticketService.js`'s `updateTicket()` that pushes a new activity type, it will silently never show up** unless you also add the matching block server-side in `server.js`'s `PUT /api/tickets/:id` (search for `newActivities.push` — there's one block per special case, plus the generic `TRACKED_TICKET_FIELDS.forEach` loop for simple field-change tracking). This bit us once already with the `apoyo_solicitado` activity type — it was added client-side only at first, and the Actividad tab never showed it until the server-side block was added too.

**Data model** (`backend/db.js`): `Company`, `User` (now with a `beforeSave` password-hashing hook, plus `admin_group_id` for the `group_admin` role — see Auth model below), `Ticket` (now with `estimacion_hus`, `DECIMAL(6,1)` — "Historias de Usuario (horas)" effort estimate, resolver-group-only editable, purely informational, doesn't feed SLA), `Comment`, `Config`, `Group`, `AreaAccesoExtra`, `TicketBloqueoHistorial`, `CampoCatalogo`, `ReglaFlujo`, `TicketCampoValor`, `Notification`. `Ticket.apoyos` is a JSON array (see "Apoyos" below) — not a separate table.

**Recurring bug pattern — `ticket.group` (legacy name) vs `ticket.resolver_group_id` (id, source of truth)**: `ticket.group` was originally a name string; `resolver_group_id` is the real id and wins whenever it's set. Any group-membership check missing an `resolver_group_id ||` fallback silently drops tickets. This is fixed correctly today in `checkTicketAccess`, `GET /api/tickets`'s `whereClause[Op.or]`, `ticketService.js` (`getVisibleTickets`, `isGroupTicket`), and `Tickets.jsx`'s `applyFilters`/`deskRoleViewMatch` — always compare against `ticket.resolver_group_id || ticket.group`, never `ticket.group` alone, when adding a new check.

**Group semantics — three independent dimensions**: `area_origen_id` (requester group), `resolver_group_id`/`group` (owning/resolving group), and `apoyos[].grupo_solicitado` (a group asked to help *without* becoming the owner). `isGroupTicket()` matches requester-or-resolver *or* an apoyo grant — appropriate for "is this relevant to my group at all" (Dashboard "Totales de mi grupo"). A team's actual *queue* (Kanban columns, `deskRoleViewMatch('groupAttention', ...)`, `Tickets.jsx`'s `applyFilters` agent branch) must match `resolver_group_id || group` **or** an *active* apoyo grant for that group — never resolver-only (drops apoyo work) and never `isGroupTicket()` alone (bleeds in requester-only tickets that aren't this team's job).

**Security audit 2026-08-27 — two confirmed bypasses in `PUT /api/tickets/:id`, both fixed**: the "resolver-group-only" guards (the "take/reassign" check around `resolver_agent_id`, and the `RESOLVER_ONLY_FIELDS` check for `status`/`priority`/`bloqueado`/`estimacion_hus`/etc.) both originally gated on `data.resolver_group_id === undefined` — meaning they only activated when that field was *absent* from the payload. A caller who included `resolver_group_id` set to the ticket's *unchanged, current* value slipped past both guards (not `undefined`, but also not a real escalation, so `isEscalation` was false too) and fell through to the generic tracked-fields loop, which does no authorization check at all. In practice this meant any internal user with mere view/comment access to a ticket — e.g. its own requester — could change status/priority/blocking/estimate fields reserved for the resolver group, just by echoing the current `resolver_group_id` alongside the real change. Fixed by comparing against the ticket's *current* value, not just checking for absence, in both guards.

**Security audit 2026-08-27 — Voltik tickets (with private notes) were visible to every internal user, including ones pinned to Volcán Desk**: `GET /api/tickets`'s default branch (no `?ambito=interno`) set `whereClause.ambito = 'externo'` with **no further scoping at all** for any non-client role — `checkTicketAccess`/`sanitizeTicketForUser` also return everything unmodified for non-client roles on `externo` tickets. Combined with `ticketService.js`'s `loadTicketsFromServer()` always calling the unscoped `/tickets` first for every internal user, this meant a Volcán Desk `group_admin`/`agent` (pinned via `User.modulo`) had every Voltik ticket — every company, full descriptions, private internal notes — sitting in their browser's memory just from a normal login, visible via the Network tab with no tampering needed. Fixed by checking `User.modulo` in that branch: a non-`admin` internal user whose `modulo` isn't `'voltik'` now gets `[]` instead of the full Voltik ticket set. `admin` (the one truly global role) and Voltik-modulo users are unaffected — this only *adds* a restriction for Volcán-Desk-pinned accounts, it doesn't change Voltik's own access at all.

**Per-group catalogs in Volcán Desk (added 2026-08-27)**: Tipos, Categorías, Prioridades, and Productos (`config.types`/`categories`/`priorities`/`products`) and `CampoCatalogo` rows now all carry a `grupoId`/`grupo_id` in Volcán Desk, so each support group has its own catalog instead of one shared across all groups — this is what `group_admin` (above) actually gets to edit. Because two groups can now both name a priority "Media" without colliding, `Settings.jsx`'s priority `value` is suffixed per group (`"media__<grupoId>"`) instead of being the fixed English literal (`"medium"`) Voltik still uses — see `slugFor()` in `Settings.jsx`'s `PrioritiesConfigPage`. `configService.js`'s `resolvePriority` already accounts for this suffix; any new code resolving a Volcán Desk priority/category/type by its raw `value` string needs to too.

**`POST /api/config` was completely broken for `group_admin` for most of 2026-08-27, fixed same day**: when `GET /api/config` started filtering `types`/`categories`/`priorities`/`products` (and, later the same day, `groupBloqueoCaps`/`emailNotificationsByGroup`) to only what a `group_admin` can see, nobody re-checked `POST /api/config`'s write-side validation — which required the incoming payload's "other groups'" items/entries to be **byte-identical** to the server's current state, as its proof that the caller hadn't tampered with anyone else's data. Once GET stopped sending those other-group items at all, that comparison could never pass again — confirmed live: a `group_admin` re-saving their own priority with **zero actual changes** got `403 "No tienes permiso para modificar esta parte de la configuración."` This silently blocked every catalog edit (Tipos/Categorías/Prioridades/Productos) for every `group_admin`, for however long elapsed between the GET-filtering fix and this one, without a single successful save. Fixed by no longer diffing against the client's necessarily-incomplete payload at all: the route now takes the server's current "other groups'" items/entries as ground truth and only overlays the caller's own-group items/entries from the incoming payload (`SCOPED_SECTIONS` for the four array catalogs via the existing `belongsToOther` filter; a new `GROUP_SCOPED_OBJECT_SECTIONS = ['groupBloqueoCaps', 'emailNotificationsByGroup']` for the two per-group-keyed objects, each merged key-by-key so a missing key in the payload means "no opinion, keep the server's value" rather than "delete it"). **Any future group-scoped section added to `Config.value`** — array-of-items-with-`grupoId` or object-keyed-by-groupId — needs to go into `SCOPED_SECTIONS`/`GROUP_SCOPED_OBJECT_SECTIONS` respectively, or it will silently reintroduce this exact failure mode the moment `GET /api/config` starts filtering it for `group_admin`.

**Dynamic ticket fields (EAV-style)**: `CampoCatalogo` defines available custom fields (`tipo_dato`: texto/numero/fecha/hora/moneda/select, plus `archivo` added 2026-08-27); `ReglaFlujo` maps a ticket `tipo`/`categoria` combination to which fields apply and whether they're required; `TicketCampoValor` stores the actual per-ticket values. `GET /api/reglas-flujo/resolve` resolves the applicable rule for a given type/category. `CampoCatalogo.scope` distinguishes reusable `'flujo'` fields from `'base'` fields that are fixed per-module form fields — `'base'` fields also gained `obligatorio`/`orden` columns today and are now group-scoped too (see "Per-group catalogs" above). The new `archivo` type accepts a file upload: `processCampoArchivoValue()` in `server.js` (mirrors `processAttachments`, base64-in-JSON like the rest of the app's uploads) writes a JSON-stringified `{fileName, fileSize, fileType, fileUrl}` into `TicketCampoValor.valor` since that column is TEXT, not a dedicated attachments table — rendered as a download link in `TicketDetailView.jsx` and in `Tickets.jsx`'s create form, built from the new `API_ORIGIN` export in `api.js`. `FormFieldsConfigPage.jsx`/`FlowsConfigPage.jsx` are the admin UI for both catalogs, both gated by `group_admin` scoping (above).

**Apoyos Solicitados (cross-group "ask for help without transferring ownership")** — the biggest feature added 2026-08-26/27, ported from the sibling local repo's approved plan and then debugged live:
- `Ticket.apoyos`: `[{ id, grupo_solicitado, status: 'Pendiente'|'En progreso'|'Resuelto', fecha_solicitud, descripcion, sub_asignado? }]`.
- `ticketService.js` exports `parseApoyos`, `getApoyoActivo`, `getApoyoParaGrupo`, `getEstadoAgrupacion` (drives `TicketTable.jsx`'s collapsible per-status sections), `sortByUrgency`.
- **Critical rule, learned the hard way**: every place that checks "does my group have an apoyo on this ticket" must exclude `status === 'Resuelto'` — `getApoyoParaGrupo()` does this correctly, but it took three separate fixes to make it stick everywhere: `ticketService.js`/`Tickets.jsx` (client) already excluded resolved apoyos; `server.js`'s `checkTicketAccess` and `sanitizeTicketForUser` did **not** (a resolved apoyo kept granting ticket access / private-note visibility forever); and `GET /api/tickets`'s SQL-level `Op.or` clause does a raw `LIKE '%"grupo_solicitado":"<gid>"%'` against the JSON column — which **cannot** see the neighboring `status` field, so it always over-matches. The fix pattern: keep the coarse SQL `LIKE` as a pre-filter (it's fine to over-fetch), then apply a precise JS `.filter()` on the fetched rows afterward, re-checking `status !== 'Resuelto'` exactly like the frontend does. If you touch apoyo visibility again, grep for `grupo_solicitado` in `server.js` and check all three spots, not just one.
- UI in `TicketDetailView.jsx`: sidebar "⋮ Más acciones" menu → "Solicitar apoyo a otro grupo" opens a modal that creates **two separate comments**, not one — (1) a public, plain-text, centered "system stamp" (`data-apoyo-consulta` marker in the HTML, WhatsApp-join/leave style, visible to the requester too, rendered via `.msg-apoyo-stamp`) announcing *that* a consultation started, and (2) a private note (`data-apoyo-nota` marker, rendered with the `.msg-note-apoyo` blue-accented variant of the normal note style, label "🔎 CONSULTA DE APOYO 🔒") carrying the *actual* question — visible only to the resolver group and the group being asked. Don't merge these back into one comment; the split was explicitly requested after the merged version leaked either the wrong audience or the wrong visual treatment.
- The sidebar's "Apoyos Solicitados" panel shows only the 3 most recent (sorted newest-first) — full history already lives as stamps in the conversation. When filtering/sorting, preserve each apoyo's original array index (`originalIdx`) for status-update handlers — the array itself stays unsorted.

**Conversation view**: WhatsApp-style chat bubbles (`.msg-row`/`.msg-bubble`, classes prefixed `msg-*`), tabs for Conversación/Actividad (Volcán Desk only). **Responder/Nota/Solicitar-apoyo buttons moved 2026-08-27**: they used to render in their own bordered bar (`.ticket-top-toolbar`) below the title/progress-stepper block; now they render inline inside `.ticket-header-actions` (the row with "Volver a Tickets"), in the same right-aligned flex group as "Copiar enlace"/"Marcar como leído"/"Ver Actividad" (`marginLeft: 'auto'` pushes that whole group to the row's right edge, `flexWrap: 'wrap'` so it doesn't overflow with everything crammed in). **`RichTextEditor.jsx` file-picker race condition, fixed 2026-08-27**: `handleFileInput()` used to call `onAttachmentsChange?.([...attachments, newAttachment])` inside each file's own `FileReader.onload`, once per selected file — every one of those callbacks closed over the same stale `attachments` array (its value from when the file input's `change` event fired, not the latest state), so with 2+ files each async completion overwrote the previous one's result instead of adding to it; only the last file to finish reading survived, silently, with the others just gone. Not reachable through today's UI (the `<input type="file">` here has no `multiple` attribute, so the browser dialog only ever yields one file at a time) — confirmed while answering a question about multi-attachment behavior, fixed as a latent landmine before it could bite if `multiple` is ever added for a better multi-select UX (still not implemented — user explicitly asked to fix only the race condition, not add multi-select). Now `handleFileInput` reads every selected file via `Promise.all`, then calls `onAttachmentsChange` exactly once with the full batch appended in selection order.

**Ticket progress stepper**: `TicketProgressStepper` component in `TicketDetailView.jsx`, shown only for `ticketModulo === 'volcan_desk'`, driven purely by `ticket.status` against the fixed `DESK_PROGRESS_STAGES` sequence (mirrors `INTERNAL_STATUSES` from `configService.js`: to_do/on_going/in_testing/under_review/done). **Navigation/state persistence**: no router library. `App.jsx`'s `currentPage` is persisted to `sessionStorage['tms_current_page']` and mirrored into `window.history` state (`navigateToPage()` does `pushState`) so browser back/forward move between app pages instead of leaving the SPA entirely; a `popstate` listener restores `currentPage` on back/forward. `Tickets.jsx` does the same one level deeper for the *open ticket* (`sessionStorage['openTicketId']`, no longer deleted immediately after use like before — it's kept in sync so an F5 while viewing a ticket reopens the same one) with its own `popstate` listener guarded by an `isPopNavRef` to avoid re-pushing history when a pop event is what triggered the selection change in the first place. **Volcán Desk ticket ID scheme**: `createTicket()` in `ticketService.js` computes `interno` ticket ids as `VD-<área origen, cleaned>-<000001, global counter across all interno tickets>` — the origin group is fixed at creation and the counter is global (not per-group/prefix), specifically so an escalation that changes the *resolver* group doesn't invalidate the id, and reorganizing groups doesn't break uniqueness (documented in-code as "v3"; v1 used a single fixed `VOLCANDESK` prefix, v2 keyed the prefix off the resolver group — both rejected for the reasons above). **Security audit 2026-08-27 — attachments hardened (file-type allowlist, signed short-lived download tokens, orphan cleanup)**: three separate gaps, all fixed the same day.
- `PUT /api/tickets/:id/read` had no `checkTicketAccess` call at all — any authenticated user could flip another ticket's read/unread flag by id regardless of company/group. Fixed by adding the same check used by `GET`/`PUT /api/tickets/:id`.
- `processAttachments`/`processCampoArchivoValue` in `server.js` accepted any file extension (including `.html`/`.svg`, which a browser executes/renders if opened directly instead of downloaded) with no size cap beyond the global 50MB JSON body limit. Fixed with `ALLOWED_ATTACHMENT_EXTENSIONS` (a whitelist — documents/images/spreadsheets/archives/email, deliberately not a blacklist) and a 20MB-per-file `MAX_ATTACHMENT_BYTES` cap, both enforced in a shared `validateAttachmentFile()` that throws (rejecting the whole request, no silent partial-failure) when either check fails.
- `/api/uploads` was a bare `express.static` mount with **zero** authorization — any URL that ever leaked (forwarded email, browser history, screenshot) gave permanent, unrevocable file access regardless of later losing ticket access. Fixed by replacing it with `GET /api/uploads/:filename`, which now re-runs `checkTicketAccess` against the file's owning ticket (found via `findTicketByAttachmentFilename()`, searching `Ticket.attachments` then `TicketCampoValor.valor`) before serving. Because this route is reached via a plain `<a href>` (so attachment downloads keep working without extra client JS) rather than a `fetch()` carrying the usual `x-user-id`/`x-user-role` headers, identity can't travel as a header here — putting the raw `uid`/`role` in the URL instead was considered and explicitly rejected (would let anyone edit the URL to impersonate another user, and leaves a live credential sitting in a shareable link/browser history). Instead: `GET /api/uploads/:filename/token` (a normal `requireAuthenticated` route, called via `fetch()`/`api.js`, so real headers apply) checks access once and mints a `jsonwebtoken` (`DOWNLOAD_TOKEN_SECRET` env var, 15-minute expiry, payload `{ticketId, uid}` — **no `role`**, deliberately) that the download route then verifies by signature+expiry, cross-checks its `ticketId` against the file's actual owning ticket, and **re-derives the requester's role from the DB by `uid`** (never trusts a client-asserted role) before calling `checkTicketAccess` again. The token only prevents identity spoofing in the URL — it is not itself a permission grant; the permission decision is still `checkTicketAccess(ticket, realUser)`, identical to viewing the ticket. Frontend: `TicketDetailView.jsx`'s "archivo" field download is no longer a plain `<a href>` — it's a click handler (`handleDownloadArchivoField`) that fetches the token first, then `window.open()`s the file URL with the token attached.
- **Orphaned attachment files now get cleaned up**: removing a file from `ticket.attachments` via `PUT /api/tickets/:id` used to leave the physical file on disk forever (confirmed live during the 2026-08-27 audit — a test file survived being unlinked from its ticket). `deleteAttachmentFileIfOrphaned()` now runs after a successful update whenever `data.attachments` was part of the payload: for each `fileUrl` present in the ticket's *old* `attachments` but missing from the *new* one, it deletes the on-disk file **only if** no `Ticket.attachments`, `Comment.attachments`, or `TicketCampoValor.valor` anywhere still references that exact `fileUrl` (checked via the same JSON `LIKE` pattern used elsewhere in this file). Scoped to ticket-level attachments only, per the original ask — dynamic "archivo" field values being replaced and comment attachments being removed don't go through this path yet and can still orphan files; same for ticket deletion (`DELETE /api/tickets/:id` doesn't clean up any of the ticket's attachment files either). Worth revisiting if orphaned files become a real disk-usage problem.

**Session 2026-09-24 (continuación 3) — a real production outage (Gmail SMTP rate-limiting crashed the whole Node process, plus a client-side `localStorage` quota crash), diagnosed and fixed in prod by a separate session/tool, then ported here same day**: full incident detail is in prod's `CLAUDE.md` ("Session 2026-09-24 — Live Production Outage and Client-side QuotaExceededError fix") — this dev copy was not involved in diagnosing or fixing the incident, only in porting the resulting patches afterward. Two patches ported from `Z:\VolcanDesk-Prod` to here, confirmed byte-identical via `diff`:
