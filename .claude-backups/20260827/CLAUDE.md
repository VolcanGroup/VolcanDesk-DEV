## Commands

Two-part app: Vite/React frontend at `frontend/`, Express/Sequelize backend at `backend/`. Run as separate PM2 processes per `ecosystem.config.js` (`volcandesk-backend` → `node server.js`, port 4000; `volcandesk-frontend` → `node serve-static.cjs`, port 5173, serves the **built** `frontend/dist/`, not the Vite dev server).

```bash
cd backend && npm install && node server.js      # or: pm2 restart volcandesk-backend
cd frontend && npm install && npm run build      # serve-static.cjs reads dist/ live, no restart needed after a build
```

After editing `backend/*.js`, tell the user to run `pm2 restart volcandesk-backend`; after editing `frontend/src/*`, just run `npm run build` yourself (writes straight to `dist/`, picked up immediately since `serve-static.cjs` does a fresh `fs.readFile` per request, no caching).

- Backend `.env` needs `DB_NAME`/`DB_USER`/`DB_PASSWORD`/`DB_HOST`/`DB_PORT`; `.env.example` documents real-looking defaults in plaintext (`TktPass2026!`, `10.23.105.36`) — this is a known, flagged issue, not something to "fix" by regenerating the file blind.

## Architecture

**Client/server split**: `frontend/src/services/api.js` is the single fetch wrapper; `API_BASE_URL` is derived from `window.location.hostname` (works from any machine on the LAN, not hardcoded to localhost). Every resource has a matching service module in `frontend/src/services/`.

**Auth model (hardened 2026-08-26, was previously headers-only with plaintext passwords)**: still no real session/cookie — the client sends `x-user-id`/`x-user-role` headers read from `localStorage['tms_current_user']`, and the server trusts them at face value (`req.user` middleware in `server.js`). What changed: passwords are now bcrypt-hashed (`User` model's `beforeSave` hook in `db.js`; legacy plaintext rows are migrated transparently on their next successful login via `isBcryptHash()`), there's a real `POST /api/auth/login` route so the password never has to leave the server or be fetched by the client, and a `requireAuthenticated` middleware (valid `x-user-id` + a real role string) now gates `GET /api/tickets`, `GET /api/users`, and all ticket/notification write routes that previously had **no gate at all** (any anonymous `curl` could read every ticket, every password, or write to any ticket). `GET /api/users` also now excludes `password` from every response. **The underlying spoofability is unchanged** — anyone who can set arbitrary headers can still claim to be any user/role; closing that needs real sessions/JWT, out of scope of this pass. `RESTRICTED_TICKET_FIELDS` (ticket fields only internal roles may set) is enforced on `PUT` but **not** on `POST /api/tickets` — known gap, not yet fixed.

**Backend recomputes ticket `activities` server-side, discarding whatever the client sent** — `PUT /api/tickets/:id` does `delete data.activities` up front and rebuilds the array itself from `TRACKED_TICKET_FIELDS` plus a few special-cased blocks (escalation, apoyo-requested). **If you add client-side logic in `ticketService.js`'s `updateTicket()` that pushes a new activity type, it will silently never show up** unless you also add the matching block server-side in `server.js`'s `PUT /api/tickets/:id` (search for `newActivities.push` — there's one block per special case, plus the generic `TRACKED_TICKET_FIELDS.forEach` loop for simple field-change tracking). This bit us once already with the `apoyo_solicitado` activity type — it was added client-side only at first, and the Actividad tab never showed it until the server-side block was added too.

**Data model** (`backend/db.js`): `Company`, `User` (now with a `beforeSave` password-hashing hook), `Ticket`, `Comment`, `Config`, `Group`, `AreaAccesoExtra`, `TicketBloqueoHistorial`, `CampoCatalogo`, `ReglaFlujo`, `TicketCampoValor`, `Notification`. `Ticket.apoyos` is a JSON array (see "Apoyos" below) — not a separate table.

**Recurring bug pattern — `ticket.group` (legacy name) vs `ticket.resolver_group_id` (id, source of truth)**: `ticket.group` was originally a name string; `resolver_group_id` is the real id and wins whenever it's set. Any group-membership check missing an `resolver_group_id ||` fallback silently drops tickets. This is fixed correctly today in `checkTicketAccess`, `GET /api/tickets`'s `whereClause[Op.or]`, `ticketService.js` (`getVisibleTickets`, `isGroupTicket`), and `Tickets.jsx`'s `applyFilters`/`deskRoleViewMatch` — always compare against `ticket.resolver_group_id || ticket.group`, never `ticket.group` alone, when adding a new check.

**Group semantics — three independent dimensions**: `area_origen_id` (requester group), `resolver_group_id`/`group` (owning/resolving group), and `apoyos[].grupo_solicitado` (a group asked to help *without* becoming the owner). `isGroupTicket()` matches requester-or-resolver *or* an apoyo grant — appropriate for "is this relevant to my group at all" (Dashboard "Totales de mi grupo"). A team's actual *queue* (Kanban columns, `deskRoleViewMatch('groupAttention', ...)`, `Tickets.jsx`'s `applyFilters` agent branch) must match `resolver_group_id || group` **or** an *active* apoyo grant for that group — never resolver-only (drops apoyo work) and never `isGroupTicket()` alone (bleeds in requester-only tickets that aren't this team's job).

**Apoyos Solicitados (cross-group "ask for help without transferring ownership")** — the biggest feature added 2026-08-26/27, ported from the sibling local repo's approved plan and then debugged live:
- `Ticket.apoyos`: `[{ id, grupo_solicitado, status: 'Pendiente'|'En progreso'|'Resuelto', fecha_solicitud, descripcion, sub_asignado? }]`.
- `ticketService.js` exports `parseApoyos`, `getApoyoActivo`, `getApoyoParaGrupo`, `getEstadoAgrupacion` (drives `TicketTable.jsx`'s collapsible per-status sections), `sortByUrgency`.
- **Critical rule, learned the hard way**: every place that checks "does my group have an apoyo on this ticket" must exclude `status === 'Resuelto'` — `getApoyoParaGrupo()` does this correctly, but it took three separate fixes to make it stick everywhere: `ticketService.js`/`Tickets.jsx` (client) already excluded resolved apoyos; `server.js`'s `checkTicketAccess` and `sanitizeTicketForUser` did **not** (a resolved apoyo kept granting ticket access / private-note visibility forever); and `GET /api/tickets`'s SQL-level `Op.or` clause does a raw `LIKE '%"grupo_solicitado":"<gid>"%'` against the JSON column — which **cannot** see the neighboring `status` field, so it always over-matches. The fix pattern: keep the coarse SQL `LIKE` as a pre-filter (it's fine to over-fetch), then apply a precise JS `.filter()` on the fetched rows afterward, re-checking `status !== 'Resuelto'` exactly like the frontend does. If you touch apoyo visibility again, grep for `grupo_solicitado` in `server.js` and check all three spots, not just one.
- UI in `TicketDetailView.jsx`: sidebar "⋮ Más acciones" menu → "Solicitar apoyo a otro grupo" opens a modal that creates **two separate comments**, not one — (1) a public, plain-text, centered "system stamp" (`data-apoyo-consulta` marker in the HTML, WhatsApp-join/leave style, visible to the requester too, rendered via `.msg-apoyo-stamp`) announcing *that* a consultation started, and (2) a private note (`data-apoyo-nota` marker, rendered with the `.msg-note-apoyo` blue-accented variant of the normal note style, label "🔎 CONSULTA DE APOYO 🔒") carrying the *actual* question — visible only to the resolver group and the group being asked. Don't merge these back into one comment; the split was explicitly requested after the merged version leaked either the wrong audience or the wrong visual treatment.
- The sidebar's "Apoyos Solicitados" panel shows only the 3 most recent (sorted newest-first) — full history already lives as stamps in the conversation. When filtering/sorting, preserve each apoyo's original array index (`originalIdx`) for status-update handlers — the array itself stays unsorted.

**Sidebar architecture (`TicketDetailView.jsx`)**: collapsible sections via a local `SidebarSection` component (accordion — `openSidebarSection` is a single string, only one section open at a time) and a `ClickToEdit` wrapper (click a read-only value to reveal its editable control, click outside to close) used for Producto/Categoría/Tipo/fecha fields. Section order in "Ejecución": Estado → Etiquetas → Prioridad & SLA (with the SLA bar) → Bloqueo. The **open** section's header renders as a blue capsule (`var(--color-primary)` background, white text) — same blue as the chat bubbles — so the active section is unmistakable; closed sections are dimmed (`opacity: 0.55`).

**Conversation view**: WhatsApp-style chat bubbles (`.msg-row`/`.msg-bubble`, classes prefixed `msg-*`), tabs for Conversación/Actividad (Volcán Desk only), a `.ticket-top-toolbar` with Responder/Nota/Solicitar-apoyo buttons (no floating FAB — removed as a duplicate). **Bubble alignment is per-viewer, not per-role**: `isRight = comment.userId === currentUser.id` — your own messages are always on your right, everyone else's on your left, so two different people looking at the same thread each see their own side differently (previously it was fixed: requester always left, everyone else always right, so both viewers saw an identical layout). The very first message (the ticket description) is exempt from this — it's a fixed, always-left "reference card" (`msg-initial-card`), not treated as a flippable reply. A `commenterGroupLabel` badge ("Resolutor · <grupo>" / "Solicitante" / own group / "Admin") identifies who's talking in a multi-group thread — don't drop this when restyling. **Reply-to-quote** (`handleReplyToComment`): each message/note has a green ↩ button; replying embeds a frozen `<div class="quoted-reply" data-reply-id="...">` snippet at the top of the new comment's HTML (survives DOMPurify — `data-*` attributes pass its default allowlist), and clicking a rendered quote scrolls to and briefly highlights (`.msg-highlight-flash`) the element with `id="msg-<commentId>"` via event delegation + `closest('.quoted-reply')`, with `e.stopPropagation()` so it doesn't also trigger the parent bubble's collapse toggle.

**Ticket progress stepper**: `TicketProgressStepper` component in `TicketDetailView.jsx`, shown only for `ticketModulo === 'volcan_desk'`, driven purely by `ticket.status` against the fixed `DESK_PROGRESS_STAGES` sequence (mirrors `INTERNAL_STATUSES` from `configService.js`: to_do/on_going/in_testing/under_review/done). Purely visual — completed stages green with a checkmark, the current stage gets a colored halo (blue/blue/purple/orange/green per stage), later stages gray. No percentage.

**Navigation/state persistence**: no router library. `App.jsx`'s `currentPage` is persisted to `sessionStorage['tms_current_page']` and mirrored into `window.history` state (`navigateToPage()` does `pushState`) so browser back/forward move between app pages instead of leaving the SPA entirely; a `popstate` listener restores `currentPage` on back/forward. `Tickets.jsx` does the same one level deeper for the *open ticket* (`sessionStorage['openTicketId']`, no longer deleted immediately after use like before — it's kept in sync so an F5 while viewing a ticket reopens the same one) with its own `popstate` listener guarded by an `isPopNavRef` to avoid re-pushing history when a pop event is what triggered the selection change in the first place. Both `App.jsx` and `Tickets.jsx` `replaceState` by *merging* with `window.history.state` rather than overwriting it outright — React fires child effects before parent effects, so `Tickets.jsx`'s ticketId-anchoring `replaceState` (on mount) runs before `App.jsx`'s page-anchoring one; a naive overwrite in the parent would wipe out the child's ticketId.

**Ticket list caching**: `ticketService.js`'s module-level `cachedTickets`, populated by `loadTicketsFromServer()`. Since `GET /api/users`/`GET /api/tickets` now require authentication (see Auth model above), `App.jsx` only calls `loadUsersFromServer()`/`loadTicketsFromServer()` **after** confirming a session exists (`isAuthenticated()`) or right after a successful login — calling them unconditionally on mount (the old behavior) would 401 pre-login. `Tickets.jsx` polls every 8s.

**Voltik vs. Volcán Desk**: `ticket.ambito` (`'externo'|'interno'`), set once at creation. `externo` = Voltik (customer-facing), `interno` = Volcán Desk (cross-department internal). Same `Ticket` table, must always filter by `ambito`. `WorkspaceContext.jsx` tracks the active workspace for UI framing only, not a query filter.

**Frontend structure**: no router — `App.jsx` switches pages via `currentPage` string. `frontend/src/pages/` (Dashboard, Tickets, Reports, Users, Settings — the standalone `Kanban.jsx` page was removed 2026-08-26, unreachable from the Sidebar and had a real data-leak bug; Kanban functionality lives inside `Tickets.jsx` via `KanbanBoard.jsx`), `frontend/src/components/` (shared UI), `frontend/src/context/WorkspaceContext.jsx`, `frontend/src/utils/helpers.js`.

**Known remaining issues** (flagged, not yet fixed as of 2026-08-27): `POST /api/tickets` doesn't enforce `RESTRICTED_TICKET_FIELDS` (a client can create a pre-resolved/pre-assigned ticket); the header-based auth is fundamentally spoofable by design (no real session); `backend/.env.example` and `backend/test_dbs.js` both hardcode a real-looking DB password in plaintext; hardcoded seed credentials were already removed from `frontend/src/services/userService.js` but the auto-seed-on-empty-DB behavior it used to provide no longer has a replacement (irrelevant while the DB has real users, but worth knowing before ever resetting it from scratch).
